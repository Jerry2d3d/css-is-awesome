# Claude — Web designer (20yr) — Round 2

## Q1 — Bare-tag approach: real talk

I have shipped this exact pattern three times — once on top of an in-house "starter classless" sheet for a magazine CMS, once with Pico over a WordPress block theme, and once with a hand-rolled element-styled sheet for a Shopify storefront. It is the highest-ROI thing on a content site and the most quietly painful thing on a product app. The split is not theoretical — it follows the HTML you actually receive.

Where it wins, hard: editorial content (CMS body fields, MDX, markdown-rendered blog posts), email-style forms, internal admin panels, README/landing pages, anything where an author is dropping `<h2>`, `<p>`, `<table>`, `<ul>`, `<blockquote>` into a contenteditable. Today our `dist/css-is-awesome.css` does **nothing** for those tags — the consumer ships an unstyled `<table>` from WordPress and the page looks like 1998. `button { @include btn-base }` plus tasteful defaults for `<input>`, `<select>`, `<textarea>`, `<table>`, `<fieldset>`, `<hr>`, `<code>`, `<kbd>` is the single most valuable thing we could ship for Tier 1. It is also the thing Pico's stars are made of.

Where it bites — and these are real, not hypothetical:

1. **Form libraries that re-skin natives.** React-Select, Downshift, Headless UI Combobox, and especially **Formik with Material UI** wrap a hidden native `<input>` inside a styled shell. If we style `input` globally, the hidden one inherits our padding/border and the outer chrome shifts a pixel or knocks alignment out. Same story with **react-day-picker**, **react-datepicker**, and any "rich text" editor (Tiptap, Slate) that renders contenteditable `<button>`s for toolbar items — those will inherit `btn-base` focus rings and you spend an afternoon hunting it down.
2. **Headless component libraries.** Radix, Ark, Reach — they emit semantic `<button>`s for menu triggers, dialog closes, accordion headers. All of those will pick up our `display: inline-flex; gap; padding`. You will see it on the very first Radix dropdown a consumer drops in.
3. **CMS HTML that ALREADY has classes.** WordPress emits `<button class="wp-block-button__link">`. Drupal emits `<input class="form-text">`. Our bare-tag rules will collide with theirs at specificity 0,0,1 vs 0,0,1 — last-loaded wins, which means load order becomes a contract. I have debugged that exact bug at 1am.
4. **`<button type="submit">` in third-party forms** (Stripe Checkout embeds, HubSpot forms, Mailchimp). They iframe-or-don't unpredictably. When they don't iframe, our base button hijacks their CTA. Sometimes desired, often not.
5. **The `<a>` problem.** Pico styles `<a>` aggressively. We will be tempted to. Don't, or scope it to `main a` / `article a`. Bare `<a>` styling lights up every nav link, breadcrumb, footer link, and skip-link in any consumer's site, and the override war is unwinnable.
6. **Specificity floor for our own React layer.** `Button.tsx` renders `<button class="...module...">`. If `button { ... }` sets `background: var(--action-primary-default)` at 0,0,1, every CSS Module class also at 0,0,1 fights it on source order. CSS Modules are usually loaded in `<head>` *before* our global sheet — meaning our bare-tag rule WINS over the module unless we either (a) load modules last, or (b) gate the bare rule with `:where(button:not([class]))`. Option (b) is the right answer and nobody talks about it enough.
7. **Print stylesheets and email clients.** Not your problem until it is. Worth a `@media print { button { all: revert } }` line.

Is it still mixin-first? Yes — but the framing changes. Today the mixin is the API and a class is one consumer of it. Tomorrow the mixin is still the API, but **the bare tag is the default consumer**, and `.cia-*` utilities become the deviation path, not the entry path. That is a philosophical shift Jerry should be eyes-open about. It also means we have to commit to one of: (a) every styled element is wrapped in `:where()` so authors can override with a single class, or (b) we accept that authors who want to deviate must use a class with one extra attribute selector for specificity. I would pick (a) every time — `:where(button)` is the single most underused selector in 2026 and it solves the entire override war for free.

What about variants? The right pattern, in order of taste: `<button class="primary">`, then `<button data-variant="primary">`, then attribute-natives where they exist (`<button disabled>`, `<input type="submit">`). Modifier classes win on ergonomics — every CMS author can type `class="primary"`. Data attributes win on namespace cleanliness but lose on muscle memory. Pseudo-classes are a non-starter because there are not enough of them and authors do not write them.

Coexistence with `cia-*` utilities: they survive untouched. Layout/spacing utilities are already a different layer. The only collision is the existing `.cia-bg-action-primary-default` etc. — a bare `<button>` already has that background, so the utility becomes redundant on buttons, but it is still useful on `<div class="cia-bg-action-primary-default">` cards. No conflict.

## Q2 — Top items to keep from the imported doc (ranked)

1. **Logical properties (`margin-block` / `padding-inline` over physical)** — Free RTL, free TTB, no behavioral change for LTR consumers, and our `_utilities.scss` (lines 20-49) currently emits physical-only. Single biggest "we should have done this already" item. One stylelint rule (`csstools/use-logical: always`) and a one-time utility-name migration (or aliasing) and we are done.
2. **Native interactive elements + label/htmlFor a11y** — Already our practice; codify it. Matters even more under bare-tag styling because if a consumer writes `<div onclick>` instead of `<button>`, our defaults will not save them. Lock it with a lint rule before the bare-tag world ships.
3. **No `!important` rule** — Already true by accident, but under bare-tag styling consumers WILL be tempted to reach for `!important` when a Radix button inherits something they did not want. Codify the ban on **our** code so we are forced to use `:where()` and proper layering instead. Stylelint `declaration-no-important`.
4. **Pseudo-elements over decorative DOM** — Not just stylistic; under bare-tag this matters more because we cannot rely on consumers nesting wrappers. If `<table>` needs a scroll shadow, it is `::before` on the table, not a `<div class="scroll-wrapper">` we cannot inject.
5. **TypeScript `type` for props / `interface` for data models, co-located `*.types.ts`** — Pure low-cost win, zero runtime cost. Useful when `Button.tsx`'s prop union grows under bare-tag (we will add `as`, `variant`, `size`, `iconLeft`, `iconRight`).
6. **`handle*` event-handler prefix** — Cheap consistency lint. Worth nothing alone, worth something as part of "we have house style and enforce it."
7. **Class joining via array syntax** — Already idiomatic. Codify it once we add the modifier-class API (`<button class="primary large">` from React = `[styles.btn, variant && styles[variant]].join(' ')`).

Explicit non-keepers: vanilla-CSS-only (kills the system), `*.module.css` required even when empty (contradicts Jerry's vision), root-must-be-`<section>` (breaks `Button.tsx` and `Tag.tsx`), Fibonacci as a *value* convention (our `theme-contract.json` and numbered scale already are the contract — Fibonacci is for codebases that do not have one).

## My recommendation

Ship it — but with three non-negotiables. (1) Every bare-tag rule must be wrapped in `:where()` so authors override with one class at zero specificity cost. (2) Variants ride on a single modifier class (`.primary`, `.outline`, `.ghost`) AND mirror as `data-variant` for headless-component compatibility. (3) Scope aggressive resets (`<a>`, `<table>`, `<hr>`) to a `.cia-prose` wrapper for editorial contexts only — global on `button`/`input`/`select`/`textarea`/`fieldset`/`button[type]`/`form`, scoped on the rest. Without those three guardrails I have watched this approach turn into an 80-issue backlog of "third-party widget X looks weird now" within one quarter.

The bare-tag layer should land alongside the existing utility tier, not replace it. Tier 1 readers get a styled `<button>` for free; Tier 2 React consumers keep their components; Tier 3 power users keep their mixins. Three layers, one source of truth (`scss/components/_buttons.scss`'s `btn()` router). That is the system Jerry wants and it is shippable in roughly two days of focused work — one day for the SCSS, one for the regression sweep against the `dist/` demo and the docs site.
