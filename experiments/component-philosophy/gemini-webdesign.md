# Gemini — Web designer (20yr)

## Q1 — Ideas that fit as-is
*   **Fibonacci Number Convention:** This is pure gold for a designer's mental model. It removes "pixel-pushing" anxiety and creates a shared language of "approximate vs. exact" values. 
*   **Logical Properties (`-block`, `-inline`):** Essential for a modern system intended for npm/CDN distribution. It future-proofs the library for RTL/TTB layouts without extra effort.
*   **Types Co-location:** Keeping `button.types.ts` next to the component is clean. It makes the "API" of the component discoverable without wading through implementation logic.
*   **Semantic Hierarchy (section → article → div):** Great for "Layout" components (Cards, Heros, Sections). It forces junior devs to think about document structure rather than just "box soup."
*   **Accessibility First:** The hard rule against click handlers on `div`/`span` is non-negotiable for a professional library.

## Q2 — Conflicts (and resolution)
*   **Vanilla CSS vs. SCSS Mixins:** The project is a "mixin-first SCSS system." Forcing `.module.css` (Vanilla) breaks the primary value prop: the 120+ mixins.
    *   *Resolution:* Use `.module.scss`. It allows consumers to `@use` our mixin library for overrides while keeping the "local-first" scoping of modules.
*   **Root element as `<section>`:** This is an accessibility disaster for standard controls. A `Button` must be a `<button>`, an `Input` an `<input>`.
    *   *Resolution:* The root element should be the **most semantic native element**. The `section → article` rule applies specifically to *layout-heavy* or *container* components.
*   **Required Style Module:** Jerry wants to eliminate per-component SCSS files for standard usage.
    *   *Resolution:* Make the style module **optional**. The React component should apply global "Design System Classes" (e.g., `.cia-button`) by default. The `.module.scss` file is only created when a dev needs to *break* the system.

## Q3 — Consumer authoring without per-component SCSS
From a designer's perspective, the mental model should be **"The Component is the Style."** 

The consumer shouldn't think about classes at all; they should think about **Intent**. If I want a primary button, I don't write CSS; I pass a prop. The React component acts as a "Class Mapper" to the global styles generated by our SCSS mixins.

**The Call Site:**
```tsx
// 0 lines of CSS written by the consumer
<Button variant="primary" size="large">Click Me</Button>
```

**The Mental Model:**
1.  **Global Layer:** `core.scss` generates standard classes (`.cia-button`, `.cia-input`) using the mixins.
2.  **React Layer:** Components apply these classes based on props.
3.  **Escape Hatch:** Only if you need a "One-off" (e.g., `MarketingButton`) do you create a `.module.scss` and `@include m.btn(primary)` with your custom tweaks.

## Q4 — Concrete proposal
I recommend a "Class-First, Module-Optional" structure.

**File Path Sketch:**
```
src/components/Button/
├── Button.tsx           // Logic + Prop-to-Class mapping
└── button.types.ts      // Clean API definition
(NO .module.scss by default)
```

**Button.tsx Sketch:**
```tsx
import { ButtonProps } from './button.types';

// The system provides a global 'cia-' namespace via the generator
const Button = ({ variant = 'default', size = 'md', className, ...props }: ButtonProps) => {
  const systemClasses = [
    'cia-button',
    `cia-button--${variant}`,
    `cia-button--${size}`
  ];

  return (
    <button 
      className={[...systemClasses, className].filter(Boolean).join(' ')} 
      {...props} 
    />
  );
};
```

## Tradeoffs
*   **Pros:** Extreme speed for junior devs; absolute visual consistency across the app; much smaller bundle size (no duplicate CSS modules for standard components).
*   **Cons:** Higher reliance on the "Global" CSS being loaded; slightly more complex SCSS generator logic to ensure all variations are exported as classes.
