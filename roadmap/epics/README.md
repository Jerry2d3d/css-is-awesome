> **A real bug shipped with the first publish.** `css-is-awesome` still declared its own `bin: { "css-is-awesome-mcp": "mcp/server.cjs" }` — the same command name the new package needed. Since the new package depends on core, npm links both packages' bins into the same `node_modules/.bin/`, and core's silently won: a real `npx css-is-awesome-mcp` was running core's old file, not the new package's own, proven by `serverInfo.version` reporting cia's version instead of the new package's. The existing verification script didn't catch it because it copied `server.cjs` directly into its scratch dir instead of installing the new package as a real dependency — it never exercised npm's `bin` resolution, the one mechanism the bug lived in. Fixed by removing core's colliding `bin` entry (nothing that depended on the *file* broke — every real `.mcp.json` config already used the direct `node .../mcp/server.cjs` path) and rewriting the verify script to install both packages for real and assert on the resolved bin target (POSIX-symlink-aware, not just a Windows-shaped file read) before spawning it. Confirmed the regression check actually catches the bug — fails with the collision reintroduced, passes without it — not just green either way. Full writeup: [the blog post](https://cssisawesome.com/blog/the-mcp-command-that-ran-someone-elses-file). README, AGENTS.md, `llm.txt`, `bin/README.md`, and `/docs/mcp` all updated to lead with `npx css-is-awesome-mcp` — the README and `llm.txt` previously contained an explicit warning telling people *not* to use that command, written before the package existed.

> **Audit note (2026-09-11, earlier) — v1.2 EPIC-05 (MUI/Chakra migration) complete: v1.2 is fully shipped, 8 of 8 epics.** `npx cia migrate mui` and `npx cia migrate chakra` join the existing `tailwind`/`bootstrap` tools (v1.0 EPIC-03) — one-way, token-only: read the consumer's existing MUI/Chakra theme object, map its values onto cia's own token contract, write a real `theme.scss`. Built by extending the shared mapping engine already proven by `migrate-bootstrap.cjs` (which itself reuses `migrate-tailwind.cjs`'s functions rather than forking) — Chakra's `colors`/`space`/`radii`/`fontSizes` shapes turned out to be structurally identical to what the engine already walks for Tailwind, so most of the Chakra migrator is direct reuse, not new logic. Two scope calls recorded rather than silently made: MUI's `.dark`/`.light` palette shades aren't separately mapped to hover/active (the shared writer already auto-derives those via `m.states()` once a `-default` token is set — mapping both would create two competing mechanisms); neither MUI's 24-elevation shadow array nor Chakra's shadows/breakpoints/zIndices are individually mapped (no natural 1:1 cia analog — cia's shadow set is 5 named steps, and its breakpoints/z-layers are a fixed system scale, not themed per project), surfacing as one honest informational note each instead of an arbitrary guess. Verified live against real, correctly-shaped fixture themes for both tools: MUI — 17 HIGH + 1 MEDIUM + 5 UNMAPPED, Chakra — 14 HIGH + 4 MEDIUM + 3 UNMAPPED (including a correctly-detected competing-spacing-slot collision), both compiling cleanly with `sass`. One epic-file correction made along the way: "passes `validate-themes`" as an acceptance bar doesn't actually hold for *any* fresh migration from *any* of the 4 tools — confirmed by running the identical compile+validate pipeline against a minimal real Tailwind config, which fails the same way, for the same reason (a fresh migration only has the tokens the source config defined; completing the rest is the tool's own stated purpose, not a bug). New docs pages `/docs/migration-mui` and `/docs/migration-chakra` (the real `migration-<tool>` route convention, not the epic's originally-guessed `/docs/migrate/<tool>`) actually document the CLI tool itself — usage, mapping table, worked example — unlike the existing `/docs/migration-tailwind`/`migration-bootstrap` pages, which (a pre-existing gap, not touched here) never mention the `cia migrate` tool at all despite it existing and working.

> **Audit note (2026-09-10, earlier) — density-knob F5.1 shipped: one `--space-unit` now drives all 9 spacing steps.** [v1-1 EPIC-05](./v1-1/EPIC-05-density-knob.md)'s first story is done: every one of the 24 theme SCSS files had an identical, hand-duplicated 10-line `--space-0..9` block (verified byte-for-byte identical across all 24 before touching anything) — replaced with one `@include ss.space-scale;` call into a new shared mixin (`scss/_spacing-scale.scss`). One real design change from the epic's own original "Design" section, worked out with Jerry across several turns: the per-step multipliers are **derived** at build time from `_system.scss`'s existing `$spacing-scale` map (`math.div($value, $unit)`), not hand-typed into a second table — Jerry caught that the epic's own hand-written `calc()` lines still amounted to hardcoding, and a pure "generate every integer step with no curation" alternative he proposed was checked against the actual shipped ratios and found to not be a clean formula (the 9-step scale is hand-curated, same shape as Tailwind's/Material's own default scales), so it was rejected in favor of computing from the single existing source of truth instead. Verified live via Playwright: `getComputedStyle` padding for all 9 steps across 4 sampled themes matches the exact prior px values, and overriding `--space-unit` itself live-rescales every step (tested `--space-1` doubling 8px → 16px). `build:css:themes`, `validate-themes` (now gating the new required `--space-unit` contract token), and `check:theme-drift` all pass. ## Versioned epic format

Every versioned epic file follows the structure documented in [`v1-0/README.md`](./v1-0/README.md). Standard sections: Mission, Why now, Out of scope, Features (each with user stories + acceptance criteria + effort), Definition of done, Risks, Related.

### Story IDs

`US-V<MM>.<EE>.<FF>.<SS>` where:
- `V<MM>` = version major+minor (V10 for v1.0, V11 for v1.1, V15 for v1.5, V20 for v2.0)
- `<EE>` = epic number within that version
- `<FF>` = feature number within that epic
- `<SS>` = story number within that feature

Example: `US-V11.04.1.1` = v1.1, epic 04 (@cia/react POC), feature 1 (codegen pipeline), story 1 (parse recipe markdown into AST).

### Effort scale (hours-based)

- **S** — under 4 hours
- **M** — 4 to 8 hours
- **L** — 1 to 2 days
- **XL** — more than 2 days (rare; usually a sign the story should be split)

## Cross-cutting decisions (every epic respects these)

- **Zero JS in npm `files` manifest** — CLI binaries in `bin/` allowed (MCP server already there)
- **No `@layer`** — `:where()` for bare-tag specificity
- **No BEM** — no `__` / `--` patterns in cia class names
- **No component library to maintain** — recipes are the framework story; `@cia/<framework>` packs ship via codegen if at all
- **Mixin-first** — cia is the mixin; the selector is the consumer's choice
- **Themes are data** — one theme = one file via `light-dark()`; tokens only
- **Fail-by-default a11y** — `--allow-a11y-fail` opts out; default enforces WCAG 2.2 AA

See memory in `~/.claude/projects/K--repo-css-is-awesome/memory/` for the full architectural lock history.

## How to add an epic post-lock

1. Pick the right version folder (or create one)
2. Add `EPIC-<NN>-<name>.md` following the existing structure in that version
3. Update that version's `README.md` to list the new epic
4. Update this top-level README's "Versioned epic folders" table

## How to deprecate an epic

1. Rename file → `<filename>.archived.md`
2. Add header note: `**STATUS: ARCHIVED <date>** — Reason: <one line>. See [<replacement>](path) for current direction.`
3. Update the version README to note the archive
4. Don't delete — history matters

# Legacy: original 7 epics (preserved for history)

> The structure below predates the 2026-05-23 v1.0 architecture lock. Most items have shipped (MCP server, theme validator, CI, semantic-release) or were absorbed into the new versioned epics. The "Gremlin UI" plan in particular has been REVISED — see Phase 8 in `ROADMAP.md` and [`v1-0/post-v1-ideas.md`](./v1-0/post-v1-ideas.md) for the current "boiler = showcase, not a separate React component library" direction.

## Legacy format

```md
# Epic {N}: {Name}

## Summary
One paragraph. What this epic delivers and why it matters.

## Features

### Feature {N.M}: {Name}

#### User Stories

**US-{N}.{M}.{K}** — As a {role}, I want {goal}, so that {benefit}.

**Acceptance criteria:**
- [ ] criterion 1
- [ ] criterion 2

**Priority:** P0 | P1 | P2
**Effort:** 1 | 3 | 5 | 7 | 9 | 11 | 13
```

(Legacy effort scale was modified-Fibonacci 1-13; new versioned epics use S/M/L/XL with hour ranges. Mapping: old 1 → S, 3 → M, 7 → L, 13 → XL.)

## Legacy ID scheme

`US-{epic#}.{feature#}.{story#}` — e.g. `US-1.2.3` = legacy Epic 1, Feature 2, Story 3.

(New versioned epics use the prefixed format `US-V<MM>.<EE>.<FF>.<SS>` documented above to avoid collision.)

## Legacy priority scale

- **P0** — blocker for 1.0 release.
- **P1** — wanted for 1.0, can slip without blocking the release.
- **P2** — post-1.0.
